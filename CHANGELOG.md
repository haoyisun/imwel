## [Unreleased]

### Added

- `imwel binding show`: inspect the current directory's binding and contribution tracking as two distinct local-only views. The compact summary covers remote alias/branch, linked project, modules, tools, sync refs, and counts; `--details` adds Artifact ownership, installed/source paths with `present`/`missing` status, contribution targets, and pushed Git refs; `--json` emits only a stable `schemaVersion: 1` shape. The command works with tracking alone, exposes neither credential-bearing URLs nor file contents, and never fetches, initializes history, or writes.
- `imwel tools`: adjust an existing binding's AI coding tools without rebinding its remote, branch, project, modules, frozen state, or optional selections. Added tools receive the complete current non-frozen binding through unified conflict and managed-file safety checks, while existing-tool outputs are not rewritten. Removed-tool outputs stay on disk as unmanaged files by default; `--delete-output` deletes only exact recorded paths with no remaining managed reference. Non-interactive changes use explicit `--add` / `--remove` plus `-y`.
- Versioned contribution tracking replaces one-shot pending proposals while retaining compatibility with `.imwel/pending-proposals.yaml`. `imwel propose` now selects one remote project/module before collecting candidates, reverse-parses tool-native sources into convention-derived canonical paths, preselects existing tracking in the shared toggle → diff → confirm flow, and can cancel tracking without touching local files. One local Artifact has one target; project tracking graduates after matching sync, while module tracking persists. `imwel push` records successful branch/commit SHAs, preserves unselected/failed records, skips unchanged Git content, permits explicitly tracked subscribed-module edits, and handles missing sources safely in interactive and non-interactive modes.
- `imwel template init --from-project`: cold-start a template repository from a project that already has AI coding rules scattered across its tool directories. Harvests only the user's **own** artifacts (via artifact provenance — excludes imwel's command pack and other tools' installed files, printing what/why), generates a structurally valid skeleton (`.imwel/manifest.yaml` + `rules`/`skills`/`agents.md` + scaffolded `/imwel-author`, `/imwel-lint`) into a unique `.imwel/generated-templates/<topic>-<timestamp>/` dir (or `--dir`), reports cross-tool conflicts, and leaves semantic organization to the new `/imwel-create-template` command-pack skill. Read-only over the scanned project; publishing stays plain `git`.
- `imwel-create-template` command-pack member: a first-party command + backing skill (installed with the pack) that wraps `imwel template init --from-project`, then guides splitting projects, assigning roles, and writing manifest/README — never a maintained content store.
- First-party **command pack** (foundation): imwel now delivers its first-party tools as **slash commands + backing skills** into your AI tools, the way openspec does — not as a maintained rule/skill content repo. `imwel skill install` (and, opt-in, `imwel init` via `--command-pack` / `--no-command-pack`) installs the pack into selected tools: tools with a command mechanism (Cursor `.cursor/commands`, Claude Code `.claude/commands`) get `/imwel-*` thin commands **plus** the backing skill; tools without a command mechanism degrade to skill-only. Installed files carry a `generatedBy: imwel` provenance marker and live under the `imwel-*` namespace, stay **unmanaged** (no binding/history entry, never reported as drift), and never block a bind.
- Artifact **provenance** classification (`src/core/provenance.ts`): a deterministic, offline classifier that labels artifacts found in tool directories as `MINE` (imwel-installed), `FOREIGN` (another known tool, e.g. openspec), or `USER` (your own rules), biasing uncertain cases toward `USER`. Shared foundation so future `adopt` / `template init --from-project` / `propose` only act on `USER` artifacts and never sweep in imwel's or third-party tooling's files.

- Modules & multi-project bindings: a consumer directory can now install any number of **read-only modules** (`role: shared` in the manifest — reusable standards like a Python or Vue 3 pack) alongside **at most one writable project** (`role: project`). Authors declare intent via the new optional `role` field; a missing role defaults to `project` (backward-compatible). `imwel init` groups the selection (tools, modules, writable project) behind a unified toggle → diff → second-confirm flow, and legacy single-project bindings are auto-normalized on read. New `imwel modules` command adds/removes/freezes modules incrementally. `imwel sync` walks every bound project, skips **frozen** modules, and — because modules are pull-only — never silently overwrites local edits to a module: it prompts to **discard / freeze / uninstall** (non-interactive `--yes` defaults to freeze). `imwel push` only pushes the writable project's edits; contributing back to a module is done deliberately via `imwel propose` (a reviewed PR/MR). Cross-source path conflicts are reported with their source projects. Docs (bilingual: manifest roles, `imwel init`/`imwel modules`/`imwel sync`, consumer quickstart with rebinding/multi-remote risk notes) updated.
- Rule metadata overlay (authoring side): a `rule` source file may carry a small YAML frontmatter overlay (`description` / `globs` / `alwaysApply`, plus an optional `imwel:` tool-specific block). imwel parses it into semantic overrides and strips it from the canonical body, so rules render with the right description/glob/trigger in every tool instead of degrading to the filename slug. The author overlay is the cross-tool default; a consumer's per-tool edit still takes precedence. The `imwel-extract` skill contract and the scaffolded example rule now author this overlay, and `docs/**/guide/manifest.md` documents the schema and the three trigger intents (always-on / glob-attached / agent-requested).
- Skill description propagation: when a skill is rendered as an on-demand rule for a tool without a native skills directory (cline/windsurf/kiro, …), its `SKILL.md` `description` now propagates into the generated rule frontmatter instead of falling back to the filename slug.
- `imwel adopt` redefined — **render a reviewed draft box into your tools** (local activation): `imwel adopt --from .imwel/drafts/<box>` renders that batch through the existing adapters into each tool's native location as **unmanaged** files (no binding/history entry, never reported as drift), reusing the render/dedupe/downgrade pipeline. Draft boxes are resolved from `.imwel/drafts/` (flat legacy layout, or named per-batch boxes — interactive picks, non-interactive requires an explicit `--from <box>`); target tools come from `--tools`, else the binding, else detection. The deterministic rule-health gate still runs before writing (issue count surfaced; non-interactive with issues is refused). Harvesting scattered tool rules into a canonical/template shape moved to `imwel template init --from-project`.
- `imwel-adopt` command-pack member: a first-party command + backing skill (installed with the pack) that wraps `imwel adopt --from <box>` — locates draft boxes, runs the command, and explains the health-gate/conflict results in plain language. Never renders or rewrites drafts itself.
- `imwel-extract` loop upgrade: the skill now runs `imwel scan` itself when the fingerprint is missing, writes each batch into a uniquely named draft box `.imwel/drafts/<topic>-<timestamp>/` (so repeated runs never collide), and ends with an explicit three-part handoff (box location → review → `imwel adopt --from <box>`).
- Dedicated **In-tool skills & commands** doc page (bilingual): centralizes how to install and invoke the first-party command-pack skills (`imwel-extract` / `imwel-audit` / `imwel-adopt` / `imwel-create-template`) inside AI tools, kept separate from the CLI-only `guide/commands.md` reference.
- `imwel-extract` / `imwel-audit` authoring-quality upgrade: both first-party skills now consume the `imwel scan` Git-history overlay (hotspots as rule candidates / strong missing-rule signals, co-changes as cross-file hints) with graceful fallback when history is unavailable or low-confidence, and follow an explicit authoring standard — progressive disclosure, short rules with do/don't examples, precise triggerable descriptions, evidence over guesses — plus a pre-handoff self-check. Boundaries unchanged (isolated `.imwel/drafts/` and `.imwel/audit/`, no session hooks, no full scans).
- `imwel scan` Git-history overlay: when the project is a Git repository, the fingerprint gains an optional `history` section with change **hotspots** and **co-change** pairs (with evidence counts) mined from recent commits — the highest-value places for rule authoring. Read-only, shells out to system `git`, deterministic, and degrades gracefully across three levels (full / low-confidence for new-or-shallow repos / none when there is no `.git` or no commits); `scan` prints which level applied. Never tied to any AI tool session.

- Task-oriented bilingual Usage guide (`docs/en/guide/usage.md` + `docs/zh-CN/guide/usage.md`) covering install, core concepts, consumer and template-author workflows, cold-start/rule-freshness, and troubleshooting; linked from the docs nav/sidebar and both READMEs. Added a `usage-doc-sync` Cursor rule and a docs-checklist item requiring the guide to stay in sync with user-visible changes.

- `imwel-audit` first-party skill: AI-driven semantic rule audit that flags rule↔code mismatches, rule↔rule conflicts, and missing rules using the scan fingerprint for targeted reads, writing actionable suggestions to `.imwel/audit/` (explicit invocation; never hooks the AI tool session). Installed via `imwel skill install`.
- `imwel skill install`: install imwel's first-party skills (starting with `imwel-extract`) into selected tools via the existing render adapters; first-party assets are unmanaged (not registered in the binding, history, or tracked by sync/status/push). `imwel-extract` reads the `imwel scan` fingerprint and drafts project-fit rules/skills into `.imwel/drafts/` for review.
- `imwel scan`: deterministic, LLM-free project fingerprint written to `.imwel/fingerprint.yaml` (language mix, manifests, test/lint/format/CI configs, top-level dirs, DB schema files, scattered rule-file locations) — a low-cost map for downstream AI rule authoring; inspects file names/paths only (never contents) and skips heavy directories.
- Rule health checks: deterministic, LLM-free static checks (empty/placeholder rules, dead `@import`s, orphan path references) surfaced by `imwel status` (consumer-side, advisory) and `imwel lint` (template-side, empty-only, warning level).
- `imwel adopt`: consolidate existing scattered tool-native rules/skills (`.cursor/rules`, `CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md`, …) into canonical artifacts under `.imwel/adopted/` — reverse-parses across all 14 adapters via a new `Adapter.discoverExisting`, merges identical content, surfaces cross-tool conflicts without overwriting, and runs without a binding/remote (cold start).
- Twelve additional render adapters: `trae`, `qoder`, `codex`, `opencode`, `zcode`, `gemini-cli`, `windsurf`, `continue`, `cline`, `kiro`, `copilot`, `aider` (shared strategy helpers, skill fidelity ladder R1–R4, AGENTS.md path dedupe/conflict handling).
- Documentation site depth (VitePress): bilingual Guide (architecture, manifest, commands, example template, template authoring) and Contribute (adapters) pages; `docs:dev` / `docs:build` scripts.
- Template author experience: `imwel lint`, repository context detection (`template` / `consumer` / `neither` / `ambiguous`), and Cursor slash-command / skill / rule packs scaffolded by `imwel template init`.
- Open-source release readiness: CONTRIBUTING (en/zh-CN), SECURITY, GitHub Issue/PR templates, npm package metadata, publish workflow.

### Added

- `imwel template init` scaffold: `.imwel/manifest.yaml` now carries inline comments and an example entry documenting the `role` field (`shared`/`project`, default `project`) directly where authors first look, instead of only in the reference docs (bilingual: `templates/init/en/`, `templates/init/zh-CN/`).
- `imwel lint`: new `project.artifactNameCollision` warning when two projects (any `role`) declare a rule or skill artifact with the same basename — installing both would collide on the rendered path; the message names both projects and the colliding name (warning level; `--strict` fails on it).

### Fixed

- Managed render writes (`init`, rebind, and module installation) now classify every target before writing, preserve non-imwel content in shared files, and require explicit confirmation before replacing a different unmanaged file; declining aborts before files, local history, or binding state change. `sync` now visibly restores binding-owned files deleted from disk after confirmation. `push` preflights binding and proposal inputs before Git side effects, skips missing files with recovery guidance instead of throwing `ENOENT` or inferring an upstream deletion, and separates valid candidates from skipped inputs.
- `imwel remote add` no longer silently registers a second alias for a URL that's already configured: it now rejects the add and reports the existing alias that already points at that (normalized) URL. The clone/fetch that creates the local cache now shows a spinner instead of leaving the terminal silent during `remote add`.
- `imwel init`'s branch selection no longer shows a spurious `origin` entry alongside real branches — `listBranches` was mis-parsing the remote `HEAD` symbolic-ref's short name; it now only keeps entries genuinely prefixed with `origin/`.
- `imwel init`'s "skip the writable project" option now has a readable, localized label (`init.prompt.project.none`) instead of an unexplained bare `—` symbol.
- Render-path conflict messages (`imwel init` / `imwel sync`) now name the source projects when a conflict spans more than one project (e.g. two same-named rule files from different modules), and the hint points at renaming one of the source files instead of a generic "pick a dominant target".
- `imwel modules --add` no longer silently overwrites files when a newly-added module's rendered path collides with content from a project that's already bound. It now renders the new module together with every project that stays bound (the writable project + other still-installed modules) before writing anything — same cross-project conflict detection `imwel init`/`imwel sync` already do — and aborts the whole invocation (including any `--remove`/`--freeze`/`--unfreeze` in the same call) with no writes and no binding change when a conflict is found.

### Changed

- Documentation information architecture overhaul: the docs site is reorganized by **purpose + audience** (Diátaxis-lite) instead of one flat guide list. New grouped sidebar — Getting started / Consumer path / Author path / Reference / Concepts / Contribute — with a "choose your path" landing page, per-page breadcrumbs and a consistent "Next" hand-off on every page, a new Glossary, and single-source getting-started commands. Consumer and author workflows are now ordered step-by-step tracks (`consume/**`, `author/**`); the former `example-template` and `template-authoring` pages are retired into the Author path with redirect stubs. Fully bilingual (en canonical + zh-CN mirrored).
- Onboarding UX: `imwel remote add` now accepts a single URL and derives the local alias from it (`imwel remote add <url>`), with `--as <alias>` to override; the `add <alias> <url>` form still works. `imwel init` auto-selects the remote when only one is configured (no `--remote` needed). `imwel template init` no longer prompts for a name up front — it defaults to the directory name and only asks when you opt into creating a remote repo. The bilingual Usage guide gains a two-lane (author / consumer) quick walkthrough that makes explicit that publishing a template is plain `git push` (there is no `imwel publish`).
- `imwel lint` now warns when a rule has no frontmatter `description` (`rule.descriptionMissing`) or a non-triggerable one (`rule.descriptionNotTriggerable`), at warning level for parity with the existing skill description checks (`--strict` fails on them).
- Shared modules no longer contribute a project-level `agents` file. The root instructions file (`AGENTS.md`, …) belongs to the single writable project, so a `role: shared` module's `agents` file is now **skipped at install time** (in `init`, `sync`, and `imwel modules`), and `imwel lint` emits a `module.agentsIgnored` warning when a shared module ships one (author content belongs in `rule`/`skill` artifacts, which compose cleanly). `rule`/`skill` discovery is unchanged.
